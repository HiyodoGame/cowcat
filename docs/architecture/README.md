# CowCat v2 架构文档

> 状态：**P3 完成**（策略、配置与审批协议，ADR-023~034）；**P4 模型层：T1–T7 全部落地（ADR-035~046）**；**P5 工具层：T0–T7 全部落地，七个核心工具已交付（ADR-047~054）**；**P6 前端：调研完成、T0 落表（ADR-055~060 已定）、T1 前提验证完成、T2 协议落地、T3 `serve` 与 stdio 传输落地（宿主仍是拒绝型占位，组合根见 T4a），T4 起未开工**。本目录随实现同步更新；与代码不一致时以代码和测试为准，并在同一 PR 里修正文档。

## 目标

CowCat 是一个长期分发的 npm 编程 agent。v2 的目标不是在旧代码上继续加功能，而是建立一个**可测试、可替换、可跨平台**的运行底座，再把功能按模块挂上去。

| ADR-019 | 会话头记录**实际 shell**（`kind` + 绝对 `executable`，不记可推导的 `baseArgs`/`commandFlag`），**不升 `schemaVersion`**——v2 日志格式从未发布（包为 `private: 0.0.0`），升版本是为不存在的兼容性付代价；此后**改动必填头字段即升 `schemaVersion`** | 已决定（P2 T2），见 [02-kernel.md](02-kernel.md#会话头与-schema-版本) |
| ADR-020 | 沙箱后端的**加固能力与可用性分开探测**：bwrap 能跑 ≠ 能禁用嵌套 user namespace（实测默认能建，`--disable-userns` 能堵，0.9.0 可用）。内核拒绝加固时**照常沙箱化但写进限制项**，不报成不可用；未探测就发 flag 会让第一条真实命令失败 | 已决定（P2 T5），见 [03-policy-and-execution.md](03-policy-and-execution.md#沙箱执行器p2-t5) 与调研 `p2-sandbox.md` §4.1 |
| ADR-021 | 沙箱执行器的两种拒绝分属不同错误类：**后端跑不了**（`SandboxUnavailableError`）与**后端能跑但请求满足不了**（`SandboxRequestRefusedError`，如 macOS `network: 'on'`）；两者都不可降级。私有 `/tmp` 固定 2 GiB + `--perms 1777`（实测默认是内存一半、0755）；写策略中尚不存在的路径被跳过时**必须**写进限制项 | 已决定（P2 T5），见 [03-policy-and-execution.md](03-policy-and-execution.md#沙箱执行器p2-t5) 与调研 `p2-sandbox.md` §4.4–§4.6 |
| ADR-022 | macOS 上**遍历符号链接需要对 SYMLINK vnode 的读权限**：`/var`、`/etc`、`/tmp` 本身是符号链接，而 profile 只授了 DIRECTORY 的 metadata，于是**任何人会写的绝对路径全部 EPERM**，而 profile 本身是对的。修法是与 DIRECTORY 同规则同位置补一条 `file-read-metadata (vnode-type SYMLINK)`。`subpath` 匹配的是**内核解析后**的路径（原本的判断成立）；曾试过「每条路径发两种拼写」，实测**无效**且把 deny 面扩大一倍，已删除 | 已接受（P2 T6）。见 [03-policy-and-execution.md](03-policy-and-execution.md#seatbelt-的符号链接遍历是承重的) 与 `p2-sandbox.md` §4.9 |
| ADR-023 | 裁决顺序**保留 `deny > ask > allow`，且跨裁决与规则书写顺序无关**。理由采用外部对照的原话：宽 deny 如 `Bash(aws *)` 阻止所有匹配调用，**包括同时匹配更窄 allow 的调用——allow 无法从 deny 里挖出例外**。这是安全语义而非实现便利（外部对照里 OpenCode 选了 last-match-wins，allow 能覆盖 deny）。**同一裁决内仍取数组首个命中**，这条要明说，否则配置作者会假设顺序完全无关 | 已决定（P3 调研）。见 [../research/p3-policy.md](../research/p3-policy.md) §2.5，16 条实测断言见其附录 B |
| ADR-034 | **「默认询问」必须是兜底，不能是一条规则**：`DEFAULT_RULES` 里那条 catch-all 的 `ask`（原 `mutations-need-approval`）在 T3a 被删除。因为 `decide` 按类别排序（ADR-023），一条无差别命中的 `ask` 会**遮蔽所有 `allow`**——没有任何配置能让一次写操作被允许，P3 出口标准第一条不可达，信任门控也失去意义。`decide` 在没有规则命中时本就返回 `ask`（`no-rule-matched`），那才是它该待的地方。**外部参照同样如此**：提示是默认行为，其 allow 规则因此能生效。**不改变任何裁决结果**——写/执行/网络仍被询问，只是理由文案来自兜底 | 已落地（P3 T3a）。探针 P12/P16 钉住，见 [../research/p3-policy.md](../research/p3-policy.md) §4.1 |
| ADR-024 | **`deny` 永不被短路**：无人值守模式只改变 `ask` 的归宿，`deny` 在任何模式下都执行。**有意偏离旧版**——旧版 `permissions.js:58` 让 yolo 在一切规则之前一票 `return 'allow'`，`deny` 与 `ask` 一并失效（有测试钉住）。三条理由：①否则「无人值守下按显式规则放行或拒绝」这句出口标准自相矛盾（「显式规则」不含 deny）；②外部对照的 `dontAsk` 与 `--auto` 在这一点上一致，自动模式只改变本该 `ask` 的请求；③无人值守的语义应当是**收窄**（少问、多做确定安全的事），不该是**放宽** | 已决定（P3 调研）。见 [../research/p3-policy.md](../research/p3-policy.md) §2.5 |
| ADR-025 | 配置分层定为**内建默认 → 用户级 → 项目级 → 会话级**（旧版的 CLI overrides 归入会话级）。**环境变量不作一层**，逐键决定谁赢——旧版把它当一层，产生「同机不同 shell 得到不同策略」的不可复现问题；外部对照同样选了「不是一层」。**取消 `STATE_KEYS` 这类隐式最高层**：运行时状态（信任记录、installId、theme 等）独立存放、**不参与配置合并**。旧版把两者混在一个 `state.json` 再整体套在最外层，因为 `readState()` 把全局 `config.json` 当 legacy 兜底再于项目层/环境变量/CLI 之后重放，导致其中的 STATE_KEY **被应用两次**，而 `hooks`/`permissions`/`sandbox`/`theme`/`panel`/`statusLine` 全在其中 | **已落地（P3 T2b + T3b）**：配置在 `policy/config.ts` + `adapters/config.ts`；运行时状态独立成 `ports/trust.ts` + `adapters/trust.ts`，不参与合并。见 [../research/p3-policy.md](../research/p3-policy.md) §3.6 / §5.4 |
| ADR-026 | **列表键合并而非替换**（对齐外部对照）：分层配置的用途就是「项目在用户基础上加东西」，整体替换会让用户级规则在项目里静默消失。**代价是必须回答「怎么撤销一条上层 `allow`」**——建议先用「更具体的 deny 覆盖」（deny 天然优先，见 ADR-023），**不引入 `!` 负向语法**；`!` 只在需要撤销一条 `deny` 时才必要，那属于收紧方向，留到有实际需求再设计 | **已落地（P3 T2b）**：`mergeConfig` 按层拼接列表；「撤销上层 allow」由 `deny` 天然优先解决。见 [../research/p3-policy.md](../research/p3-policy.md) §3.6 |
| ADR-027 | 规则语言改为**结构化字段**：`{ name, verdict, reason?, when: { tool?, path?, command?, risk?, network? } }`，全部 `when` 子字段可选（省略即「不限」）。**否决**函数式 `matches`（配置无法表达函数，与出口标准直接矛盾）与纯文本 DSL（旧版 `perrules.js:67` 的 `matchRule(rule, toolName, input)` 三参签名锁死了表达力上限——无 risk、无 network、无参数子字段；外部对照也自认文本规则不可靠）。**路径匹配委托 `FsPort`**，不在策略层重实现 glob；`command` 用**前缀语义**并在文档写明不含 `&&`/管道感知。`ActionRequest` 要扩形状（加 `input`/路径/命令），但**不必进日志**——`policy.decided` 只带 `Decision`，所以这是免费改动 | **已落地（P3 T1 + T2a）**：T1 把 `Rule.matches` 换成 `Rule.when` 并提供 `validateRules`；T2a 让 `ToolSpec.pathInput` / `commandInput` 声明路径与命令字段、由 `run-turn.ts` 生产（`path` 过 `FsPort.canonical`）。见 [../research/p3-policy.md](../research/p3-policy.md) §4.4 |
| ADR-028 | 信任门控改为**不对称**（对齐外部对照）：未信任时 **`deny` / `ask` 立即生效，`allow` 不生效**。逻辑是**收紧不需要授权、放宽才需要**。旧版「一刀切 `setMode('plan')`」粒度太粗——它连「明确 deny 的工具」都要走 plan 闸门，而 plan 闸门放行的 `READ_ONLY` 白名单包含 `CronCreate`、`ScheduleWakeup` 这类**会改状态**的工具。信任判定本身沿旧版实测语义：**按目录身份精确匹配、无继承**（子目录必须自己被信任过），记录按 canonical 路径存。**门控的粒度由 T3a 定为按来源**：`default` / `user` / `session` 的 `allow` 不受门控，只有 **`project` 层的 `allow`** 等信任——理由是字面执行「未信任时 allow 一律不生效」会连内建的 `reads-are-free` 一起废掉，变成每次读文件都问；外部参照的粒度同样是按来源。见 ADR-034 对同类问题（默认值的位置）的处理 | **门控已落地（P3 T3a）**：`policy/trust.ts` 的 `trustedRules()`；配置层来源标注在 `policy/config.ts` 的 `SourcedRule.origin`。信任记录的存储仍待 T3b。见 [../research/p3-policy.md](../research/p3-policy.md) §5.4 |
