## #1 `-p` 挂起 + 信号清理孤儿（P0）

**根因**：`cowcat.mjs:667` print 分支 `return`，早于 `:1095` 的 `background.killAll()`；SIGINT handler（`:383-386`）只杀 `runningChildren`（Bash 前台子进程），后台 registry 与 MCP stdio server 均不在列；SIGTERM 无任何处理器。

**方案**：

1. 提取 `cleanupChildProcesses()`（紧邻 SIGINT handler 定义）：
   - `background.killAll()` — registry 已有 `killAll()`
   - `mcpCleanup()` — 但 `mcpCleanup` 定义在 `:453`，晚于 handler。将函数定义（非调用）提升到 handler 之前，或用 `let` 声明后赋值。做法：把 `mcpCleanup` 改成 `let mcpCleanup = () => {}` 提前声明，452 行后再赋真实实现；或直接把清理逻辑内联一个新函数 `killAllMcpClients()`。选后者更直白：定义 `function mcpCleanup()` 提前（内部引用 `mcpClients`，`mcpClients` 在 `:416` 已创建，顺序上 383 之前不存在——所以最干净的是把 `const mcpClients = new Map()` 也提前？太碎）。
   
   **最终做法**：SIGINT handler 移到 MCP 段之后不可行（handler 需要 early）。改为：handler 内调 `background.killAll()`，MCP 清理通过 `baseCtx.mcpClients`（`:417` 已挂到 baseCtx，且早于 383）遍历 `.stop()`。`baseCtx.mcpClients` 正是 Map。所以 handler 里：
   ```js
   const killAll = () => {
     for (const c of runningChildren) { try { c.kill(); } catch { /* already dead */ } }
     background?.killAll();
     for (const client of (baseCtx.mcpClients?.values() ?? [])) { try { client.stop(); } catch { /* noop */ } }
   };
   process.on('SIGINT', () => { killAll(); process.exit(130); });
   process.on('SIGTERM', () => { killAll(); process.exit(143); });
   ```
   注意 `background` 定义在 394（晚于 383）。同样问题。解决：把 `const background = new BackgroundRegistry()` 连同 `baseCtx.background = background` 从 393-395 **上移到 382 之前**（`runningChildren` 定义处），`baseCtx` 定义本身在 387 —— 需要在 background 定义前 baseCtx 存在…… 387 定义 baseCtx 时引用了 `state`、`session` 等。
   
   简化决策：把整个「进程清理」收敛成一个**定义在 REPL 尾部的 `shutdown(code)` 函数 + 一个 `let shutdown = null` 占位**：handler 里 `shutdown ? shutdown() : null; process.exit(...)`。`shutdown` 在 main 后段（mcp/background 都定义后）赋值：
   ```js
   shutdown = () => { try { mcpCleanup(); } catch {} try { background.killAll(); } catch {} if (tui) tui.close(); };
   ```
   handler 保持不变只杀 runningChildren（前台 Bash 已有覆盖）+ 调 `shutdown?.()`。这样避免移动大段代码，风险最低。print 分支 `return` 前同样调 `shutdown?.()`。

2. print 分支（602-668）的 4 个 `return` 点前统一清理。做法：把 `if (opts.prompt) { ... }` 块改为 try/finally：
   ```js
   if (opts.prompt) {
     try { ...原有逻辑... } finally { shutdown?.(); }
   }
   ```
   `return` 在 try 内仍会触发 finally。`--background` 路径的 `finishBackgroundRun`/`notify` 发生在内层，finally 在其后执行——notify 完成后 killAll 无副作用（notify 是 powershell 子进程，独立）。

3. SIGTERM：`process.on('SIGTERM', () => { shutdown?.(); process.exit(143); });`

**不改的边界**：print 模式下主动等待后台任务完成 vs 立即杀。选立即杀——`-p` 语义是一次性出结果，模型若开了后台任务说明它打算异步；但 `-p` 的调用方（CI）拿不到 TaskOutput 的异步结果，保留进程只是挂起。杀前在 stderr 打一行提示（`stream-json` 模式除外，其 ui.print 已被静音，走 `process.stderr` 无污染——实际上 stream-json 模式写 stderr 也可能污染？stream-json 消费 stdout，stderr 安全）。

**测试**（`agent/test/lifecycle.test.mjs` 已存在，看其风格）：
- 新增 `agent/test/p0-shutdown.test.mjs`（或并入 lifecycle）：
  - `killAll()` 杀 exec 子进程：`reg.start('node -e "setTimeout(()=>{},30000)"')` → `killAll()` → `snapshot().running === false`，且 200ms 内 `task.done`。
  - 事件循环不被 hold：测试进程自然退出即证明（node:test 会因挂起而卡住——这本身就是断言）。
  - Windows 兼容：`node -e` 跨平台可用；`killAll` 在 win32 走 taskkill，`running` 标志由 `stop()` 同步置位，不依赖进程真死。

## #2 MCP 工具无法被权限规则覆盖（P0）

**根因**：`perrules.js:21` 的 `knownTools.includes(tool)` 校验用启动时快照（`cowcat.mjs:268`，MCP 连接在 452 行之后才发生）；另外 `RULE_RE`（`perrules.js:9`）的 tool 名只允许 `\w`，`mcp__srv__get-issue` 这类带 `-` 的 MCP 工具名**连解析都过不了**（第二个隐藏坑）。

**方案**：

1. `perrules.js`：
   - `RULE_RE`：`/^([A-Za-z][\w]*)\s*(?:\((.*)\))?$/s` → `/^([A-Za-z][\w.-]*)\s*(?:\((.*)\))?$/s`（放开 `-`/`.`；内建工具名不受影响，仍受首字符字母约束）
   - `validateRule`：`knownTools.includes(tool)` 前加 MCP 动态工具豁免：
     ```js
     const isMcpTool = /^mcp__[A-Za-z0-9_.-]+__[A-Za-z0-9_.-]+$/.test(tool);
     if (!isMcpTool && !knownTools.includes(tool)) { ... 原报错 ... }
     ```
2. `bin/cowcat.mjs`：
   - `applyRules` 内的 `knownTools` 从 const 快照改为实时：`loadRules(config, registry.list().map((t) => t.name))`
   - `/permissions add`（:854）同样用实时列表
   - `connectMcp()` 完成后（:452 之后）再 `applyRules()` 一次，让 config 里预置的 mcp 规则立即生效（warnings 此时为真实结果，启动早期那次对 mcp 规则的 warning 消失——顺序：452 行连接后才重跑，用户看到的是最终态）
3. 权限匹配本身无需改：`decide()` 按 `rule.tool === toolName` 逐字匹配，适配器名一致即可命中。

**测试**（扩充 `agent/test/p1-wave1.test.mjs`）：
- `validateRule('mcp__fake__echo', [])` → 接受（原来报「未注册」）
- `validateRule('mcp__srv__get-issue', [])` → 接受（RULE_RE 放宽）
- `validateRule('mcp__fake__echo(x:*)', [])` → `prefix: true, pattern: 'x'`
- 否决：`validateRule('mcp__', [])`、`validateRule('mcp___x', [])`、`validateRule('mcp__a_b', [])` 仍报错
- `loadRules` 含 mcp 规则 → `warnings.length === 0`，规则进入 allow/deny/ask
- `Permissions.decide('mcp__srv__echo', {...})` 在 allow 规则命中时返回 `'allow'`（不弹审批）

## #5 startAsync 子代理杀不掉（P1）

**根因**：`background.js:95` `task.child.pid` —— startAsync 任务的 `child` 恒为 `null`，TypeError 被 `catch {}` 吞掉；`spawnAgent` 也没有取消入口（`runLoop` 本身已支持 `signal`，`loop.js:333` 透传给 `provider.chat`）。

**方案**（两层修复）：
1. `background.js`：
   - `startAsync(fn, { timeout, description })` 内部创建 `AbortController`，存为 `task.abort = () => ac.abort()`，`task.signal = ac.signal`
   - `stop()`：先 `task.abort?.()`；再 `const child = task.child; if (child) { ...原 kill 逻辑... }`；child 为 null 时只改状态不 throw
   - `snapshot()`：aborted 且 done 后给出 `(killed)` 之外的可辨语义——`exitCode` 已置 137，够用
2. `subagent.js`：`spawnAgent({ ..., signal = null })`，透传 `runLoop({ ..., signal })`
3. `tools/agent.js` background 分支：
   ```js
   const ac = new AbortController();
   const task = reg.startAsync(() => ctx.spawnAgent({ ..., signal: ac.signal }), { description, onAbort: () => ac.abort() });
   ```
   `onAbort` 由 registry 在 stop() 时调用（即 `task.abort`）。
4. 取消后的可观测：`spawnAgent` 内 runLoop 的 signal 被 provider.chat 接收，下一轮 streaming 中止；fn reject 后 `.catch` 记 stderr。TaskOutput 随后返回 `(killed)` + exit 137。

**测试**：
- `stop()` 对 startAsync 任务：不抛错；`task.done === true`；`exitCode === 137`；`killed === true`
- `signal` 贯通：`startAsync(fn)` 的 fn 收到 `task.signal`；stop 后 `signal.aborted === true`
- agent.js background 分支传出的 spawn 参数含 signal（用 fake spawnAgent + fake registry 验证）

## L3 cron 在 `-p` 下不工作 + TUI cron 回合丢输入（P1）

**根因 A**：cron 扫描只在 REPL `while` 循环里（`cowcat.mjs`），`-p` 分支提前 return → 一次性模式永远不触发定时任务；CI 场景下没有常驻 REPL，定时任务实际上无处可跑。
**根因 B**：REPL 先 `await` cron 回合再 `readLine()`；TUI 的文字输入只在 `_reading` 非空时进编辑器（`tui/ui.js:1080`），该窗口内敲的字被丢弃。

**方案**：
- `-p`：在用户 prompt 之前执行 due cron 回合（静默，不污染 stdout——`runTurn` 在 print 模式下不流式、不打最终答案）；`[cron] firing` 提示在 print 模式下写 stderr。
- REPL：TUI 下把 `readLine()` 提前到 cron 扫描之前（composer 在扫描期间就是激活态，输入进入编辑器不丢），行模式保持「先提示符后读」的原有顺序（stdin 队列天然缓冲）。

**测试**：
- `p3-cron`：print 模式的 due 扫描顺序（cron 回合先、用户 prompt 后）用纯函数/片段验证；E2E 走 stub server 断言 `-p` 下 cron 回合确实执行且 stdout 只有用户 prompt 的答案。
- 行模式回归：`/exit`、cron 触发顺序不变。

## 联调新发现并修复的缺陷

**D1（P1，Windows 阻塞）：文档里的 `"command": "npx"` 在 Windows 上完全起不来。**
Node 24 不允许无 shell 直接 spawn `.cmd`：`spawn('npx')` → 异步 `ENOENT`，`spawn('npx.cmd')` → **同步 `EINVAL`**。而 USAGE 的 MCP 示例正是 `"command": "npx"`，Windows 用户照文档配置时一个 server 都连不上（且原有单测用 `process.execPath` 起 fixture，正好绕开了这条路径）。
修复：直接启动失败且错误码属 `ENOENT/EINVAL/UNKNOWN` 时，经 `cmd.exe /d /s /c` 重试一次；用 `windowsVerbatimArguments` 避免 Node 对已转义的命令串二次加引号（否则 cmd 会去找名字叫 `"npx"` 的程序）；`.exe`/绝对路径仍走原路径，零行为变化；重试自身失败时抛回**原始**错误。

**D2（P1，随 D1 出现）：shim 启动下 `stop()` 只杀 `cmd.exe`，真实 server 变孤儿。**
Windows 下 `child.kill()` 只终止直接子进程，`cmd → npx → node` 链里真正的 server 是孙进程。
修复：Windows 下 `stop()` 改用 `taskkill /pid <pid> /t /f` 回收整棵进程树（`%SystemRoot%\System32\taskkill.exe`，取不到则回退普通 kill）；POSIX 保持 SIGTERM → 宽限期 → SIGKILL。

**D3（P2，诊断）：任何 server 启动失败都只报 `server exited (code 1)`。**
stderr 被完全丢弃，而 server 启动失败的真实原因通常就在最后一行 stderr（`Missing API key`、`unknown option`）。修复：保留最后一行 stderr（折叠空白、上限 400 字符）并拼进退出错误。

## 联调修正的既有判断

- 第二轮修复 #3（`notifications/initialized` 改真通知）：真实 SDK server **容忍**旧的「带 id 当请求发」写法（`tools/list` 在通知前就已返回工具），只是把该请求回以 `-32601 Method not found`。因此这条属**规范正确性**而非阻塞缺陷——原文「依赖服务端容忍未匹配 id」的表述准确，但不应被理解为「旧代码在真实 server 上会失败」。实测记录见 `agent/test/live/notify-negative.mjs`。

## D9（P1，互操作）：服务器保持 SSE 流打开 → 每个请求卡到超时

**现象**：对手写服务器（应答后不关闭 SSE 流）发 `tools/list`，客户端 **3005ms 后被 abort**；`COWCAT_MCP_TIMEOUT` 默认 60s，即生产环境下每个 MCP 调用都要等满 60s 再失败。

**根因**：`HttpTransport.request()` 写成 `const text = await res.text()` —— 把整个 body 缓冲完才开始解析。Streamable HTTP 的响应流**允许在应答后保持打开**（SSE 注释帧 keep-alive、后续 server→client 消息），规范只说服务器*可以*关闭。所以「等流结束」在合法服务器上是「等一个已经回答完的服务器」。

**为什么此前没发现**：官方 SDK 的 node transport 在写完响应后就关流（实测 `keepAliveMs` 场景 41/18/14ms 通过，keep-alive 帧计数为 0），所以此前的联调都是「流会关」的那一类。

**修法**：改为增量读取——用 `res.body.getReader()` 逐块解码，扫完整行，**拿到 `id` 匹配的帧立即返回并 `reader.cancel()`**；普通 JSON body（无 `data:` 前缀）走原 `_parseBody` 路径；无 `body` 的假 fetch（单测 mock）保持回退到 `res.text()`。同一场景实测 **3ms**。

**回归测试**：`test/p4-mcp-hardening.test.mjs` —— 假 fetch 返回一个「先给应答帧、然后只发 keepalive、永不关闭」的 `ReadableStream`，断言解析出正确结果且 <1s 返回。

## 小修复：`resources/list` 也要走 cursor

`listResources()` 原样只请求一次，服务器分页时第 2 页起的资源对模型隐形——与之前 tools/list 的分页缺陷同类（那次已修 tools，漏了 resources）。现在循环 `nextCursor`（上限 50 页）。fixture 的 `FAKE_MCP_PAGE` 同时作用于 resources，新增测试。

# 第九轮：MCP server→client 通道（2026-10-16）

> **实施状态：完成。** 全量 **592 passed / 0 failed**；6 个联调脚本全部通过。方案与决策见 `docs/mcp-server-channel-plan.md`。

## 做了什么

| 能力 | 实现 |
|---|---|
| SSE 解析 | 新 `src/sse.js`：空行分帧、**多行 `data:` 用 `\n` 拼接**、`id:`/`retry:`、注释帧、CRLF、跨块切帧、`flush()`。POST 响应体与 GET 长连接共用 |
| 入站分发 | `transport.onMessage` → `McpClient._handleServerMessage` → `onNotification`。此前无 `id` 消息 **stdio 直接丢弃**、POST 流里被注释成「nothing to hand back」跳过 |
| GET SSE 长连接 | connect 后打开（带 session id）；断线退避重连（1s 起、指数、封顶 30s、5 次）+ `Last-Event-ID`；**404/405 只探一次**；`stop()` 中止 |
| server 发起请求 | `sampling`/`elicitation`/`roots` → `-32601`（HTTP POST 回、stdio 写回）；`ping` → `{}` |
| logging | 连接时发 `logging/setLevel`（`COWCAT_MCP_LOG_LEVEL`，默认 info）；`notifications/message` → 一行 |
| 订阅 | `SubscribeMcpResource`/`UnsubscribeMcpResource`（catalog §15/§16）+ `src/mcpsubs.js`（id `mcp:<server>:<uri>`，可按三要素任一退订） |
| 通知呈现 | `src/mcpnotify.js` 纯函数：log / list-changed（自动刷新，500ms 合并）/ resource-updated（仅在订阅过时提示）/ 其余显式忽略 |
| 只读分类 | `ListMcpResources`、`ReadMcpResource` 进 `READ_ONLY`（plan 模式可读）；订阅类仍需授权 |

## 实现中踩到并修掉的两个自身缺陷

1. **退避计数重置错误**：最初在「fetch 返回 200」时就重置重连计数，于是「接受连接后立刻断开」的 server 每次尝试都被算成功 → **无限重连**。改为「真的收到过帧」或「连接存活 ≥ 5s」才算健康（有测试：3 次尝试后放弃、只报一次错）。
2. **订阅登记与首条更新的竞态**：server 可能在 `resources/subscribe` 应答后立刻推 `resources/updated`，此时工具还没把订阅写进登记表 → 更新被当成「没订阅过」丢掉。改为**先登记再发请求**，失败回滚（E2E 实测命中并锁住）。

## 由此修掉的两个自身缺陷（已锁测试）

1. **抽取器把无关流当页面文本扫**（P2）：原来 inflate 每一个 Flate 流，嵌入字体程序/ICC/XMP 元数据都被扫，二进制垃圾混入正文并拉低可打印比例 —— 证据：一份 1MB 英文规范 `Type0`=0（无 CID 字体）却量出 33% 非可打印。改为按**当前对象**的字典跳过字体/图片/元数据/对象流；`/Form` 故意不跳过（页面文本可以合法地存在于 form XObject）。

## CI 第一跑的结果：三个 job 失败，全部定位并修复

| ubuntu 上 node 20/22/24 全崩（`p1-wave2.test.mjs` 的 hooks 用例） | **产品缺陷**：`src/hooks.js` 往 hook 子进程 stdin 写入时，若 hook 已退出（不读 stdin / 超时被杀）会异步抛 **EPIPE**，没有流级 `error` 处理器 → 未捕获异常崩掉整个进程；Windows 不复现所以本机一直没暴露。随之 `state.json` 没写成，跑了同一条用例的第二个断言（ENOENT）——即三个 job 的失败其实是**同一个根因** | 给 `child.stdin` 加 `error` 处理器（EPIPE 在这里是正常的）+ 回归测试 |

## 补记：守卫脚本被 CRLF 弄坏（同一轮发现并修复）

把 `.githooks/pre-push` 纳入版本控制后，用 POSIX `sh` 直接跑它做白盒验证时立刻报错：

```
.githooks/pre-push: line 11: set: -: invalid option
set: usage: set [-abefhkmnptuvxBCEHPT] [-o option-name] [--] [-] [arg ...]
```

原因：本机 `core.autocrlf=true`，而仓库**没有 `.gitattributes` 约束**，于是 Git 检出时把这个脚本写成了 **CRLF**（实测 36 个 CRLF、0 个 LF）；POSIX shell 下带 `\r` 的 `set -eu` 是硬错误，shebang 同理。`tools/*.sh` 早年就是以 LF 入库的，所以一直没暴露——也就是说这是「**跨平台仓库里 shell 脚本的行尾是功能问题，不是风格问题**」，而且只在用 POSIX shell 跑的那一侧（钩子、CI、macOS/Linux 克隆）暴露。

修法：新增 `.gitattributes` 把整棵树钉成 `* text=auto eol=lf`（二进制交给 text=auto 识别），并重新检出该钩子。白盒复查（用 `sh` 分别灌三种 refs）：

| 模拟的推送 | 期望 | 实测 |
|---|---|---|
| `refs/tags/v9.9.9` | 放行 | 退出码 **0** ✓ |
| `refs/heads/feat/x` | 放行 | 退出码 **0** ✓ |
| `refs/heads/main` | 拦截 | 退出码 **1**，输出 blocked 提示 ✓ |
